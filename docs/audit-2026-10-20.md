# Cora audit: security, bugs, unfinished features (2026-10-20)

A read-only sweep of build/v1 (five parallel reviews of the server, client, desktop app and integrations), before
Cora goes to other people. **✔** marks findings checked by hand; the rest are from code reading and should be confirmed
while fixing. Inventory: [features.md](features.md).

Cora runs on your PC, binds 127.0.0.1 only, and gates the dashboard with a token cookie. The main risks are therefore not
"someone on the internet": they're **other people's words** (Jira, Slack, email, web pages) steering an agent that can act,
**anything else running as you** (another app, a local web page, a Claude session) borrowing Cora's tokens, and **data
loss or confusing failures**.

## Status (2026-10-20)

Every item is fixed on the build branch, except where noted. The findings below describe Cora before the fixes (S10 and
S11 included).

- **S1–S19:** fixed.
- **B1–B18:** fixed.
- **U1–U8:** fixed, with these notes:
  - U4: "no Jira detail in the Inbox" is left as is; the Inbox links to the ticket.
  - U5: project-scoped MCP servers and claude.ai connectors are deliberately not counted. Cora's agent runs in its own
    folder, and connectors aren't in a file.
  - U8: documented (Windows only, unsigned installer, WSL sessions not seen), not built.

## Severity

- **High**: someone else's text, a local web page or another session can make Cora do or reveal something without you.
- **Medium**: needs another foothold first, leaks something sensitive locally, or loses your data.
- **Low**: wrong, confusing or wasteful; no harm beyond that.

## Security

### High

| # | Finding | Where | Fix |
|---|---|---|---|
| S1 ✔ | **A Jira ticket's description becomes a session's first prompt, started on its own.** In "start it on its own" mode, anyone who can edit a ticket assigned to you writes the opening instructions of a session that runs with folder trust and no human in the loop. "Stop at a plan" is the only guard. | `shared/src/jira.ts` `coraTicketPrompt`; `orchestrator/jiraStart.ts:153` | Mark the description as someone else's words (quoted, defused, "information, not instructions"); make auto-start open a plan-mode session; consider dropping "on its own" for tickets from others. |
| S2 ✔ | **Cora's agent holds the dashboard sign-in link** (`/auth?key=<uiToken>`) in its prompt, and has a browser it can click with. It could sign in to Cora's own UI and approve its own cards, turn on away mode or widen its mandate; prompt-injected, it could also send the key out. | `orchestrator/files.ts:249`; Playwright click/press allowed | Never put the UI token in the agent's prompt; give screenshots a separate read-only path, or a token that only renders. |
| S3 | **Any session can act as Cora.** `/mcp` trusts the session id each caller sends (`x-cora-session`); every hosted session's MCP file holds the same hook token, and Cora's session id is visible. Sending Cora's id unlocks start/send/end sessions, decide prompts, DM you. The same token also lets anything start any program through the terminal host. | `mcp.ts:614`; `hosted.ts:84`; `ptyhost/host.ts` | A separate secret for Cora's agent (only in its own MCP file); per-session tokens; a separate host token not written into Claude's config. |
| S4 ✔ | **Any local web page can read everything.** The dashboard's WebSocket checks the cookie but not the Origin; the cookie is sent to any `localhost`/`127.0.0.1` port. A page from a local dev server (or a session's preview) can open `/ws` and read every session, prompt, pending request, Slack/email item. | `app.ts:1333` (`/pty` does check) | Check Origin on `/ws` like `/pty` and every POST. |
| S5 ✔ | **Command injection through Jump.** A session id from a transcript file name goes unescaped into a PowerShell script; a crafted `~/.claude/projects/…/x'; calc; '.jsonl` runs code when you click Jump. | `terminal.ts:43` | Validate ids (`^[\w-]{8,80}$`) wherever they enter (tailer, hooks) and before use; pass them as data, not script text. |
| S6 ✔ | **Arguments injected through Resume/Fork.** The session id is passed to `claude --resume <id>` unchecked (a value like `--dangerously-skip-permissions` becomes a flag; with the npm `.cmd` shim, shell metacharacters reach cmd.exe). | `app.ts:1194` → `pty.ts` | Same id validation; require a known session. |
| S7 | **Autopilot rules have gaps.** The mandate engine misses `&` as a separator, `$( )`, backticks and redirects, `env`/`timeout` wrappers, `node -e`/`python -c`/`npx`/`npm run`, `find -delete`, `sed -i`, `..` in paths, `docker -v /:/host`, `git -c core.sshCommand`. Matters with a goal or away mode on. | `orchestrator/mandate.ts` | Parse properly (or be stricter: anything not clearly safe asks you); normalise paths; tests per bypass. |
| S8 | **Someone else's words act on your turn.** Held Gmail/Jira lines are put in front of your next words, so that turn counts as yours: action tools run with email or comment text in context. Email lines also don't trip the "someone else's turn" lock, and that lock still leaves Read/WebFetch/browser/`gmail_watch`/`answer_question` open (exfiltration). | `orchestrator/manager.ts:134, 419-432`; `server.ts:105` | Deliver held lines as their own turn under the lock; mark them all consistently; widen the lock to every tool that sends or reads outside. |
| S9 ✔ | **Files outside the session can be attached or read.** The Slack-attachment folder check is the wrong way round (a session in your home folder can attach `~/.cora/*.json` keys and `brain.db`); a hook-supplied cwd or a transcript path lets `/changes` read any file; a hook `agent_id` with `../` reaches other files. | `slackFiles.ts:31`; `changes.ts:54-102`; `toolDetail.ts:50` | Always exclude `~/.cora`, `~/.ssh` etc.; contain paths after resolving; validate ids. |

### Medium

| # | Finding | Where | Fix |
|---|---|---|---|
| S10 | Secrets are plain JSON in `~/.cora` (Slack user/app/bot tokens and client secret, Google refresh token and client secret, ElevenLabs key); `mode 0600` does nothing on Windows; `google-client.json` has no mode at all. | `slack.ts`, `gmail.ts:217`, `voice.ts` | Encrypt with Windows DPAPI (Electron `safeStorage`) or at least restrict the ACL. |
| S11 ✔ | Tokens in logs and backups: the UI sign-in link is printed to `server.log` (which the splash asks you to open and share); every hooks write leaves a backup of `settings.json` with the hook token, never cleaned up. | `cli.ts:70`; `settings.ts:120` | Don't log the key; keep only the newest backup. |
| S12 | Electron: the main, capture and popout windows use the default session with no permission handler (a popped-out HTML explain runs scripts and could get mic/camera without asking); webview popups have no navigation guards; any non-web URL goes to `shell.openExternal`; a tool on `x.github.io` grants permissions to all of `github.io`. DevTools are on in installed builds. | `main.ts:102,137-143,447`; `browser.ts:22,44,126` | Deny-by-default permission handler on every session; guard popups; allow-list schemes; use a proper registrable-domain check; hide DevTools when packaged. |
| S13 ✔ | `ELECTRON_RUN_AS_NODE=1` leaks into every hosted session and shell (installed builds): Electron apps started from them (VS Code, Slack, Playwright) start as plain Node. | `runtime.ts:33`; `pty.ts` `cleanEnv` | Drop it in `cleanEnv` and the host's environment. |
| S14 | The dev-bump guard trusts the environment's label, which you can change and which is guessed with "dev" before "prod" (`prod-devices` becomes dev). The bump is the only write to a cluster. | `environments.ts:44`; `deploys.ts:242` | Check prod first; confirm a relabel to dev; show the cluster name on the bump card. |
| S15 | `open_tab` is pre-allowed: a prompt-injected session can send data out in a URL, or trigger GET actions on sites you're signed in to. | `hosted.ts:92` | Ask the first time per site, or allow only well-known hosts silently. |
| S16 | The Google client's `token_uri` isn't checked: a doctored client file sends your code and refresh token elsewhere. | `gmail.ts:53` | Accept only Google's endpoints. |
| S17 | The desktop app trusts whatever answers on port 4317 and hands it the tokens. Token comparisons aren't constant-time. | `desktop/src/server.ts:6`; `app.ts` | Verify the server (e.g. it proves it knows the token); `timingSafeEqual`. |
| S18 | Slack and Jira text returned to tools isn't wrapped as untrusted the way email is. | `mcp.ts` (slack_read/search/inbox); `manager.ts:439` | Wrap and defuse like `gmail_read`. |
| S19 | Playwright MCP is fetched as `@latest` through `npx -y` at every agent start. | `orchestrator/files.ts:70` | Pin a version. |

## Suggested order

1. **Before anyone else installs it:** S1–S6, S9, S13, B1, B3. Each is small (validation, an origin check, an exclusion,
   not writing a token), and together they close the paths where a ticket, a web page, a file name or another session
   reaches your machine.
2. **Before autopilot or away mode for others:** S7, S8 (the mandate and someone-else's-turn handling), S18.
3. **Before a public release:** S10–S12, S14–S17, B2, B4–B12, U3.
4. **Polish:** the rest.
